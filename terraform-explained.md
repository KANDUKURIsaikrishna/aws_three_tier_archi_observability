# Terraform folder, explained — file by file, module by module

Personal reference doc, not part of the repo's real documentation (that's `docs/ARCHITECTURE.md`, `docs/DEPLOYMENT.md`, `docs/UML.md`, `docs/DR-STANDBY-PLAN.md`). Tracked on the `dr` branch only (gitignored on `main`) — this branch is where the content actually applies, since Parts 1–3 below cover `main`'s single-region state and Part 5 covers this branch's own `enable_dr_standby` addition. Written 2026-08-23 against `main` post CloudWatch/CloudTrail/GuardDuty removal, extended 2026-08-29 with Part 5 after the `dr` branch's first real live two-region apply. If the code changes further, this can go stale — treat it as a snapshot, not a live doc.

Everything lives under `terraform/`. Root-level `.tf` files are cross-cutting resources not owned by any one module (IAM, ArgoCD bootstrap, ACM, CloudFront, DR). `terraform/modules/` holds 8 reusable modules, each a self-contained piece of infra.

---

## Part 1 — Root-level files

### `versions.tf`
Declares the Terraform version floor (`>= 1.10.0`, needed for native S3 state locking via `use_lockfile` — no DynamoDB table) and every provider this project uses: `aws`, `helm`, `random`, `null`, `tls`, `kubernetes`, and `kubectl` (the `gavinbunney/kubectl` provider specifically, not HashiCorp's — its `kubectl_manifest` resource defers schema validation to apply time, which matters because `argocd.tf` applies ArgoCD's own CRD-backed YAML in the same apply that installs the CRDs via Helm).

Also holds the `backend "s3"` block — `bucket` and `region` are deliberately left as empty strings. Terraform resolves backend config before any variable is evaluated (a real HCL limitation, not a bug), so those two fields can never reference `var.aws_region` — `scripts/init-backend.sh` patches the literal values in before the first `terraform init`.

### `providers.tf`
Configures every provider block. Three `aws` provider instances: the default (region = `var.aws_region`), `aws.secondary` (region = `var.secondary_region`, used by `dr.tf`'s cross-region backup replication), and `aws.us_east_1` (hardcoded — CloudFront ACM certs must live in `us-east-1` regardless of where anything else runs, an AWS hard requirement).

`helm`, `kubernetes`, and `kubectl` providers all authenticate the same way: `exec { command = "aws", args = ["eks", "get-token", ...] }` — no static kubeconfig, a fresh token generated per Terraform run via the AWS CLI. The `helm` provider also isolates its repo cache (`repository_config_path`/`repository_cache` pointed at `.terraform/helm/`) so a stale Helm repo left over from some unrelated project on the operator's machine can't cascade-fail every `helm_release` here.

### `variables.tf`
All root-level variable declarations, most with a validation block. Notable ones:
- `aws_region` / `secondary_region` — region-agnostic by design, both validated against a `^[a-z]{2}-[a-z]+-\d$` regex. `secondary_region` defaults to `us-west-2` and is always required (the `aws.secondary` provider alias needs *some* value even if DR is off), but doesn't turn DR on by itself — see `enable_dr_replication`.
- `enable_dr_replication` — off by default. Used to silently default to "on" just because `secondary_region` was non-empty (which it always was), creating live cross-region Secrets Manager/ECR replicas nobody asked for. Now an explicit separate flag.
- `domain`, `github_repo`, `alert_email` — the three values with no safe default; `scripts/configure.py` is what actually fills these into `terraform.tfvars`, never hand-edited.
- `primary_alb_dns` / `secondary_alb_dns` — leave empty; `argocd.tf` auto-discovers `primary_alb_dns` within the same apply now (see that file below).
- `dr_kms_key_id` — empty by default (DR replication skipped); a cross-region CMK is required because AWS-managed keys can't replicate across regions.
- `monitoring_admin_cidr` — defaults to `0.0.0.0/0` (open), meant to be narrowed in production.
- `extra_admin_principal_arns` — additional IAM ARNs granted EKS cluster-admin, on top of whoever is running `terraform apply` (always auto-included, see `main.tf`'s `module.eks` call).

### `locals.tf`
The VPC CIDR (`170.20.0.0/16`) and the subnet map. AZ names come from `data.aws_availability_zones.available` (in `data.tf`), not hardcoded — this used to be `"us-west-1a"`/`"us-west-1c"` literally, which broke `apply` outright in any other region. 8 subnets total: 2 public, 6 private (indices 0–3 for EKS nodes, alternating AZs; indices 4–5 for RDS, one per AZ for Multi-AZ). `eks_node_subnet_cidrs` slices out just the 4 EKS-node subnet CIDRs, used to scope the RDS security group to actual node traffic instead of the whole VPC CIDR.

### `data.tf`
Two data sources used across the whole config: `aws_caller_identity.current` (account ID, used everywhere an ARN needs to be built) and `aws_availability_zones.available` (feeds `locals.tf`'s AZ resolution).

### `main.tf`
The orchestration file — wires every module together plus a handful of root-level resources that don't belong in any module:
- **`module.network`**, **`module.security_groups`**, **`module.rds`** — straightforward module calls, each just passing in the right IDs/CIDRs from the module before it.
- **Per-service DB credentials** — a `for_each` over a local map (`catalog`/`user`/`order`/`notification`) generates one random password + one Secrets Manager secret per service, all sharing the same RDS instance but each with its own schema/DB user (schema-level isolation, not full per-service RDS — deferred as out of scope). Replaced what used to be ~110 lines of 4 near-identical copy-pasted blocks.
- **JWT secret** — one shared HS256 secret (`random_password`, 64 chars, no special chars — goes straight into an env var) that `user-service` signs with and `api-gateway`/`order-service` verify against.
- **`module.route53`** — passes `local.primary_alb_dns` (auto-discovered, see `argocd.tf`) as the ALB hostname for the failover A records.
- **`module.ecr`** — 6 repos (frontend + 5 microservices), `secondary_region` empty unless `enable_dr_replication` is true.
- **`null_resource.cleanup_eks_networking`** — destroy-time only. EKS's own workloads create two resource types directly via the EC2 API, entirely outside Terraform's graph: orphaned VPC CNI ENIs (left behind if a node terminates before the CNI's own cleanup runs) and the EKS "cluster security group" (auto-created as a side effect of `CreateCluster`). Both can block `module.network`'s VPC/subnet destroy with `DependencyViolation` if left behind. `module.eks` has `depends_on = [null_resource.cleanup_eks_networking]` — deliberately, since Terraform destroys in *reverse* dependency order, this makes `module.eks` destroy FIRST and this resource's destroy-time provisioner run SECOND (the ENIs aren't actually orphaned until the nodes that owned them are gone). Runs `scripts/cleanup_eks_networking.py` via `interpreter = ["python3"]`.
- **`module.eks`** — cluster name `bookstore-eks`, version 1.31, `t3.medium` nodes, min 1 / max 3 / desired 3 (a `t3.medium` caps at 17 pods due to the ENI IP limit — 2 nodes filled up once all 5 microservices + 2 api-gateway replicas joined). `admin_principal_arns` always includes whoever is running `terraform apply` (`data.aws_caller_identity.current.arn`), concatenated with any extra ARNs from `var.extra_admin_principal_arns`.
- **SES SMTP setup** — `aws_sesv2_email_identity` (triggers AWS's verification email to `var.alert_email`; SES starts in sandbox mode, so both sender and recipient must be verified — using the same address for both means one email to click), an IAM user + scoped `ses:SendRawEmail` policy + access key, and a `null_resource` (`ses_smtp_password`) that shells out to `scripts/derive_ses_smtp_password.py` to run AWS's documented HMAC-SHA256 SigV4-derivation algorithm (no Terraform-native HMAC function exists for this) and writes the result straight to Secrets Manager. The derived password itself never touches Terraform state.
- **`aws_eip.monitoring`** + **`module.monitoring_ec2`** — the standalone EC2 instance running the whole observability stack. Deliberately has NO blanket `depends_on = [module.eks_addons]` — it only needs `module.eks` (cluster name, cluster SG) and the Grafana secret's ARN (already an implicit dependency, and one of the fastest resources in `eks_addons`, not gated on any of the slow Helm installs). It DOES have an explicit `depends_on = [null_resource.ses_smtp_password]`, since the ARN reference alone only orders against the empty secret shell, not the local-exec that actually populates it.
- **`module.eks_addons`** — explicit `depends_on = [module.eks, module.network]`. The `module.network` dependency exists specifically so the NAT gateway (needed for the AWS Load Balancer Controller's ALB teardown to reach AWS APIs during a real `terraform destroy`) doesn't get destroyed concurrently and strand the controller mid-cleanup with no internet egress.

### `argocd.tf`
Two jobs: (1) apply ArgoCD's own YAML (`k8s/argocd/appproject.yaml`, `application.yaml`, `applicationset-microservices.yaml`) via `kubectl_manifest`, reading the files straight off disk (`file("${path.module}/../k8s/argocd/...")`) so they stay the single source of truth and can't drift from an HCL re-expression. The AppProject applies first (`depends_on` chain), since ArgoCD rejects an Application naming a project that doesn't exist yet. (2) Auto-discover the real ALB hostname within the same apply — this used to need a second `terraform apply` (Route53 couldn't create its alias record until the ALB existed, and it didn't exist until after `eks-addons` finished). Now: `null_resource.wait_for_alb_hostname` runs `scripts/wait_for_alb_hostname.py`, which polls for the `bookstore-ingress` Ingress object to exist (ArgoCD deploys it asynchronously, not Terraform directly), then `kubectl wait`s for the AWS Load Balancer Controller to populate its hostname. `data.kubernetes_ingress_v1.bookstore` then reads that hostname, and `local.primary_alb_dns` falls back to it unless `var.primary_alb_dns` is explicitly set as a manual override.

### `iam.tf`
The GitHub Actions OIDC role (`bookstore-github-oidc-role`) — lets CI assume an AWS role via `sts:AssumeRoleWithWebIdentity`, no static AWS keys in GitHub ever. The trust policy's `StringLike` condition uses wildcards after the owner/repo names (`repo:OWNER*/REPO*:ref:...`) because GitHub's OIDC token `sub` claim isn't always the classic `repo:OWNER/REPO:ref:...` shape — some accounts' tokens come through as `repo:OWNER@ownerId/REPO@repoId:ref:...` with numeric GitHub IDs appended, which a literal match rejects outright. Scoped to 3 branches: `main`, `improvements`, `observability`. The role's only inline policy (`github_oidc_ecr`) grants `ecr:GetAuthorizationToken` (account-wide, required by the API) plus push actions scoped to `bookstore-*` repos only. Notably: this role has no Terraform-apply permissions in this file — it's scoped to image push, not infra changes.

### `ingress-cert.tf`
The ACM certificate the ALB actually uses (regional, wherever the cluster lives — different from `cloudfront.tf`'s cert, which is hard-required to be in `us-east-1`). Covers `*.<domain>` AND `*.bookstore.<domain>` — the second SAN exists because `*.<domain>` only covers one label deep, which doesn't include `api.bookstore.<domain>` (two labels deep), a real gap that left the AWS Load Balancer Controller unable to find a matching cert for that Ingress until the second wildcard was added. No ARN from this cert gets injected into any Kubernetes manifest — the AWS Load Balancer Controller auto-discovers a matching *issued* ACM cert by comparing each Ingress's `spec.tls[].hosts`/`spec.rules[].host` against what's in the account, which sidesteps a chicken-and-egg problem (the cert doesn't exist until `terraform apply` creates it, but the Ingress YAML is static content ArgoCD deploys on its own schedule, decoupled from any Terraform run). Runs the full DNS validation loop (`aws_route53_record` for each validation option + `aws_acm_certificate_validation`) since the controller's auto-discovery only matches ISSUED certs, not pending ones.

### `cloudfront.tf`
Fully optional (`count = var.enable_cloudfront && var.primary_alb_dns != "" ? 1 : 0` on both resources) — off by default. When enabled: an ACM cert in `us-east-1` (via the `aws.us_east_1` provider alias) covering the domain + `www.` subdomain, and a CloudFront distribution with the ALB as a custom HTTPS origin, one path-based cache behavior for `/static/*` (long TTL, cacheable) and a default behavior with `min_ttl=default_ttl=max_ttl=0` (effectively pass-through for everything else, since this is a dynamic app, not a static site).

### `dr.tf`
One resource: `aws_db_instance_automated_backups_replication`, gated on `var.dr_kms_key_id != ""`. Cross-region RDS backup replication needs an explicit customer-managed KMS key in the secondary region — AWS-managed keys are region-scoped and can't be used for this. Uses the `aws.secondary` provider alias.

### `observability-rbac.tf`
A `ClusterRole` + `ClusterRoleBinding` (applied via `kubectl_manifest`, same pattern as `argocd.tf`) that lets the monitoring EC2's Prometheus scrape two things it otherwise couldn't: kubelet's `/metrics/cadvisor` directly on each node (real per-pod CPU/memory usage — `kube-state-metrics` only has requests/limits/status, never actual usage) and each app pod's own `/metrics` via the API server's pod-proxy (pod IPs aren't reachable from outside the cluster network the way node-hosted processes are). Bound to a stable RBAC group (`monitoring-metrics-readers`), not the raw principal ARN directly — because the monitoring EC2's IAM role, when assumed, maps to a k8s username that embeds the specific EC2 instance ID, which would break any RBAC binding on instance replacement. The access entry (in `modules/monitoring-ec2/main.tf`) sets the group; this file just grants permissions to it.

### `outputs.tf`
Every value another script or a human running `terraform output` needs: RDS endpoint + all 5 DB credential secret ARNs (catalog/user/order/notification + the original `rds_secret_arn`), all 6 ECR repo URLs, EKS cluster name/endpoint/OIDC ARN, the GitHub OIDC role ARN, Route53 zone ID + nameservers, all 4 monitoring URLs (Grafana/Prometheus/Loki/Alertmanager), the auto-generated monitoring SSH key (marked `sensitive`), Grafana's secret ARN, the CloudFront domain (`null` when disabled), and the JWT secret ARN.

## Part 2 — Modules (`terraform/modules/`)

### `network`
Resources: `aws_vpc.main` (`170.20.0.0/16`, DNS support + hostnames on), `aws_subnet.public`/`aws_subnet.private` (both `count`-based off `locals.tf`'s subnet list, not `for_each`), `aws_internet_gateway.igw`, `aws_eip.nat` + `aws_nat_gateway.nat` (single instance, placed in `public[0]` — single-AZ, a deliberate cost tradeoff for a tech demo, not HA), `aws_route_table.public`/`aws_route_table.private` + their `_association` resources, and `aws_vpc_endpoint.s3` (Gateway type, attached to *both* route tables — free, keeps ECR image-layer pulls and Terraform state reads off the NAT gateway's per-GB data-processing fee). Own module-scoped `data.aws_region.current` used only to build the S3 endpoint's `service_name`.

Exact subnet layout (from `locals.tf`, both AZs alternating):
| Index | CIDR | AZ | Purpose |
|---|---|---|---|
| public[0] | `170.20.1.0/24` | az_a | NAT lives here |
| public[1] | `170.20.2.0/24` | az_b | |
| private[0-3] | `170.20.3.0/24` – `170.20.6.0/24` | alternating | EKS node subnets |
| private[4-5] | `170.20.7.0/24`, `170.20.8.0/24` | one each | RDS subnet group (Multi-AZ) |

No dependencies — this is the very first thing to provision. Outputs: `vpc_id`, `public_subnet_ids`, `private_subnet_ids`.

*(As of 2026-08-23: no longer creates VPC Flow Logs or any CloudWatch log group — that whole piece, plus its destroy-time `force_delete_flow_log_group` cleanup workaround, was removed. The module's checked-in `README.md` is stale on this point — it's an auto-generated `terraform-docs` file nobody's regenerated since.)*

### `security`
Resources: `aws_security_group.rds` (name `${prefix}-rds-sg`) + one rule, `aws_security_group_rule.rds_mysql_in` — ingress only, 3306/tcp, source = `var.eks_node_cidr_blocks` (the 4 EKS-node subnet CIDRs specifically, not the whole VPC — that was a real bug, RDS used to be reachable from every subnet in the VPC including the public ones). No egress rule at all — the comment in the file states it plainly: "RDS does not initiate outbound connections." Output: `rds_sg_id`.

### `rds`
Resources: `random_password.db_password` (32 chars, custom `override_special` charset), `aws_secretsmanager_secret.db_credentials` (`/bookstore/db-credentials`, `recovery_window_in_days = 0`, an optional `dynamic "replica"` block that only materializes if `var.secondary_region != ""`), `aws_secretsmanager_secret_version.db_credentials` (`DB_HOST` = `.address`, deliberately not `.endpoint` — see below), `aws_db_subnet_group.rds_subnet_group`, `aws_db_instance.db`, and `aws_secretsmanager_secret_rotation.db_credentials` (`count` gated on `var.rotation_lambda_arn != ""`, off by default — needs the AWS-provided single-user rotation Lambda deployed separately, not included here).

The actual instance, as called from root `main.tf`: `db.t3.micro`, MySQL `8.0`, `db_name = "test"` (this specific database is a leftover from the original monolith design — the real per-service databases `catalog_db`/`user_db`/`order_db`/`notification_db` are provisioned separately, via root `main.tf`'s own `for_each` over `local.db_service_credentials`, not by this module), `db_username = "admin"`, `allocated_storage = 25` with `max_allocated_storage = 100` (gp3 autoscaling ceiling), `multi_az = true`, `backup_retention_period = 7`, backup window `03:00-04:00`, maintenance window `Mon:04:00-Mon:05:00`, `storage_encrypted = true` with `kms_key_id = null` (AWS-managed key), subnets = `private_subnet_ids[4]` and `[5]` (the two RDS-dedicated ones from the table above). `skip_final_snapshot = true` and `deletion_protection = false` — both flipped for a project that gets destroyed/recreated often during development; reconsider both before using this as a template for anything meant to stay up.

`DB_HOST = aws_db_instance.db.address`, not `.endpoint` — `.endpoint` is `"host:port"` combined, which every consumer expecting a bare hostname (`mysql2`'s `host:` param, the `mysql` CLI's `-h` flag) fails to resolve. This was a real, previously-shipped bug: no DB connection in this project's history ever actually worked until it was fixed, since `.endpoint`'s port suffix isn't a valid hostname on its own.

*(As of 2026-08-23: no longer sets `enabled_cloudwatch_logs_exports`, no CloudWatch log group for error/general/slowquery logs, and no RDS Enhanced Monitoring — `monitoring_interval`/`monitoring_role_arn` and the dedicated IAM role for it are gone. The only visibility into RDS load left in this stack is whatever each microservice's own connection-pool metrics expose on its app-level `/metrics` endpoint.)*

### `route53`
**Private zone**: `aws_route53_zone.rds_private` (name `var.rds_private_zone_name`, default `bookstore.internal`, associated to the VPC) + `aws_route53_record.rds_endpoint` (CNAME, name `var.rds_record_name` default `db.bookstore.internal`, TTL 100, value = RDS's endpoint). This is how in-cluster services resolve the DB without hardcoding the RDS endpoint string anywhere else.

**Public zone**: `data.aws_route53_zone.public` — *looked up*, never created/destroyed by Terraform. Creating it as a resource would mean brand-new nameserver values on every destroy+apply cycle, breaking the domain registrar delegation every single time. `scripts/init-domain.sh` creates it once, ever, outside Terraform (see Part 3 below).

Public-zone records, all in this module:
- `aws_route53_record.primary` — apex A/ALIAS, `PRIMARY` failover routing, tied to `aws_route53_health_check.primary` (HTTPS, port 443, path `/`, `failure_threshold = 3`, `request_interval = 30`). `count = var.enable_cloudfront ? 0 : 1` — active only when CloudFront is off.
- `aws_route53_record.primary_cf` — same apex, but aliased to the CloudFront distribution instead, using CloudFront's fixed AWS-wide hosted zone ID (`Z2FDTNDATAQYW2`, same in every account/region — not a data source). `count` gated on `enable_cloudfront && cloudfront_domain != ""`.
- `aws_route53_record.frontend` / `aws_route53_record.api` — the actual app hostnames, `bookstore.<domain>` and `api.bookstore.<domain>`. These were genuinely missing for a while: every earlier record only covered the bare apex, and the ALB's default rule 404s on anything that doesn't match a configured Ingress host — the site was never actually reachable by name until these were added.
- `aws_route53_record.secondary` — apex **ALIAS** (was CNAME until the `dr` branch's first live apply proved that illegal — Route53 rejects a CNAME at the zone apex, RFC 1035), `SECONDARY` failover routing. `count` gated on a dedicated `create_secondary_record` bool, not `secondary_alb_dns != ""` directly — see Part 5 for why that distinction matters once `enable_dr_standby` is in play. Aliases against `data.aws_lb_hosted_zone_id.ingress_lb_secondary` (a second, `aws.secondary`-provider-scoped copy of the same hosted-zone-ID lookup `primary` uses — region-specific constant, us-west-2's differs from us-west-1's).

All the ALIAS records use `data.aws_lb_hosted_zone_id.ingress_lb` with `load_balancer_type = "application"` to resolve the right hosted-zone-ID constant for aliasing at the ALB — this one data source has tracked three different load balancer types across this project's history (Classic ELB → NLB → ALB, as ingress-nginx was tried, half-migrated to NLB, then fully replaced by the AWS Load Balancer Controller), and picking the wrong `load_balancer_type` value is exactly what broke DNS resolution twice before it landed on the current, correct one.

### `ecr`
`locals.repos` = `["${prefix}-frontend"]` concatenated with `["${prefix}-${r}"]` for each of `var.extra_repos` (`catalog-service`, `user-service`, `order-service`, `notification-service`, `api-gateway`) — 6 repos total. `aws_ecr_repository.this` (`for_each`): `image_tag_mutability = "IMMUTABLE"`, `force_delete = true`, `scan_on_push = true`, AES256 encryption. `aws_ecr_lifecycle_policy.this` (`for_each` over the repos just created): one rule, `tagStatus = "any"`, `countType = "imageCountMoreThan"`, `countNumber = var.image_retention_count` (default 10), `action = expire`. `aws_ecr_replication_configuration.secondary`: `count` gated on `var.secondary_region != ""`, replicates into that region using `PREFIX_MATCH` on `var.prefix` — every `bookstore-*` repo, not a hand-picked subset.

### `eks`
`aws_kms_key.eks_secrets` + `aws_kms_alias.eks_secrets` — dedicated CMK for Kubernetes Secrets envelope encryption at the API layer (CIS EKS Benchmark expectation; without it, Secrets are only protected by etcd/EBS volume encryption underneath). `deletion_window_in_days = 7`, `enable_key_rotation = true`.

`aws_eks_cluster.this`: name `bookstore-eks`, version `1.31`, `access_config.authentication_mode = "API_AND_CONFIG_MAP"`, `endpoint_private_access = true` and `endpoint_public_access = true` (both on — `public_access_cidrs` defaults to `0.0.0.0/0`, meant to be narrowed for anything beyond a demo), `encryption_config` pointing at the KMS key above scoped to `["secrets"]`. `depends_on` includes the cluster IAM role's two policy attachments, the KMS inline policy, and (as of 2026-08-23) nothing CloudWatch-related — `enabled_cluster_log_types` isn't set at all, so no control-plane logs (api/audit/authenticator/controllerManager/scheduler) ship anywhere.

`aws_launch_template.nodes`: gp3 20GB encrypted root volume (`delete_on_termination = true`), IMDS `http_tokens = "required"` with `http_put_response_hop_limit = 2` (containers on the node need one extra hop past the node itself to reach IMDS), `lifecycle { create_before_destroy = true }`. Its `user_data` renders `node-user-data.sh.tftpl`, which installs **node-exporter v1.8.2** and **Fluent Bit** as systemd services directly on the node — not Kubernetes DaemonSets, since the whole point of this design is running zero monitoring pods inside the cluster (see `monitoring-ec2` below for where they actually feed into). Fluent Bit discovers the monitoring EC2's *private* IP at boot via `aws ec2 describe-instances` (retried, 10 attempts / 6s apart, to survive an IAM-propagation race on the node's own freshly-created describe-instances permission) — a static IP baked in via `templatefile()` would need to be the monitoring EC2's *public* Elastic IP (the only value available without a circular module dependency), but traffic from a private subnet to another instance's public IP within the same VPC doesn't route back cleanly (no public-IP hairpinning), so runtime discovery is the only thing that actually works here.

`aws_eks_node_group.this`: `instance_types = [var.node_instance_type]` (`t3.medium`), `ami_type = "AL2_x86_64"`, `scaling_config` = min 1 / max 3 / desired 3 (as called from root `main.tf` — the module's own variable defaults are lower, min 1 / max 2 / desired 1, overridden at the call site), `update_config.max_unavailable = 1`. Currently carries `lifecycle { ignore_changes = [launch_template[0].version] }` — a real rollout of the Fluent Bit fix is pending an EC2 vCPU quota increase (8→16 requested, not yet cleared as of the last check — see the account's actual `L-1216C47A` quota, confirmed live at exactly 8.0), deliberately paused rather than shrinking node count into an already-tight pod-capacity margin. `t3.medium` caps at 17 pods per node from the ENI IP limit, not CPU/memory — worth remembering before assuming "add more replicas" is free.

`iam.tf` (inside this module): cluster role gets `AmazonEKSClusterPolicy` + `AmazonEKSVPCResourceController` + a scoped KMS `Encrypt`/`Decrypt`/`DescribeKey` inline policy (defense-in-depth — EKS creates its own KMS grant on cluster creation using the calling principal's permissions, so this isn't strictly required, but keeps the role self-sufficient regardless of who ran `apply`). Node role gets `AmazonEKSWorkerNodePolicy` + `AmazonEKS_CNI_Policy` + `AmazonEC2ContainerRegistryReadOnly` + a scoped `ec2:DescribeInstances` inline policy (exactly the permission the Loki-IP-discovery lookup above needs, nothing broader).

Admin access entries (`aws_eks_access_entry` + `aws_eks_access_policy_association`, both `for_each` over `var.admin_principal_arns`, policy = `AmazonEKSClusterAdminPolicy`) exist because `bootstrap_cluster_creator_admin_permissions` only fires once, at the literal `CreateCluster` API call — it doesn't retroactively grant access to whoever runs `terraform apply` later, and doesn't survive a module refactor that state-moves the cluster resource without recreating it. These entries are the persistent, re-appliable equivalent; root `main.tf` always includes `data.aws_caller_identity.current.arn` in the list, so whoever is running Terraform right now always has cluster-admin regardless of who created it originally.

OIDC provider: `data.tls_certificate.eks` fetches the cluster's own OIDC issuer's cert, `aws_iam_openid_connect_provider.eks` registers it with a single audience (`sts.amazonaws.com`) — this is what every `eks-addons` IRSA role's trust policy federates against.

### `eks-addons`
Everything Helm-installed on top of the cluster, all concurrent — no artificial serialization between charts (that used to exist purely for single-node resource contention, back when the cluster ran fewer nodes; removed to shorten apply time, with a note in `gitops.tf` that it's the fix to re-reach for if a real apply starts timing out again, not "raise node count further"):

- **`external-secrets.tf`** — `helm_release.external_secrets` (`external-secrets/external-secrets`, namespace `external-secrets`, `timeout = 900`, `installCRDs = true`). Standard IRSA pattern: `aws_iam_role.external_secrets` trusts the OIDC provider scoped via `sub`/`aud` conditions to exactly `system:serviceaccount:external-secrets:external-secrets-sa`, its inline policy grants `secretsmanager:GetSecretValue`/`DescribeSecret` on `/bookstore/*` only.
- **`aws-load-balancer-controller.tf`** — `helm_release.aws_lb_controller`, chart version pinned at `3.4.0`, namespace `kube-system`, `timeout = 300`. Replaces `ingress-nginx` entirely (officially retired by the Kubernetes project on 2026-03-31 — no more CVE patches for something directly internet-facing, a real security liability, not a style choice). Its IAM policy (`aws_iam_role_policy.aws_lb_controller`) is the official ~15-statement policy fetched verbatim from the controller project's own `iam_policy.json`, not hand-written — re-diff against that file before bumping the chart version by more than a patch. `depends_on = [aws_iam_role_policy.aws_lb_controller, aws_eks_addon.vpc_cni]`, combining two separate real incidents into one list: (1) without ordering against the policy, the controller's first reconcile hit `UnauthorizedOperation` on `ec2:DescribeSecurityGroups` — reproduced live, twice, since the `set` block only references the role's ARN, not its policy, so Terraform had zero ordering constraint between them by default; (2) `vpc_cni` has to outlive this controller on `terraform destroy`, or new pods become unschedulable mid-teardown once the CNI socket disappears. Also owns `null_resource.delete_ingress_objects` (destroy-time only) — deletes Ingress objects before `terraform destroy` reaches the VPC (releasing the ALB's finalizer), then polls (up to 20 minutes) for the controller's shared backend security group to clear before the VPC delete can succeed.
- **`ebs-csi.tf`** — `aws_iam_role_policy_attachment.ebs_csi_policy` (`AmazonEBSCSIDriverPolicy` on the node role) then `aws_eks_addon.ebs_csi` (managed EKS addon, not a Helm chart).
- **`vpc-cni.tf`** — explicitly manages `aws_eks_addon.vpc_cni` (which EKS already creates implicitly at cluster creation, `resolve_conflicts_on_create = "OVERWRITE"` adopts it instead of erroring), specifically to set `configuration_values = jsonencode({ enableNetworkPolicy = "true" })` — a top-level field, not the older env-var-style toggle earlier CNI versions used (AWS restructured this at some point; re-check `aws eks describe-addon-configuration --addon-name vpc-cni` before touching it again, don't assume from a doc). Without this, every `NetworkPolicy` manifest under `k8s/` is inert — Kubernetes just stores the objects, nothing enforces them, since the built-in network-policy agent (shipped since VPC CNI 1.14/EKS 1.25) has to be explicitly turned on. Same file also creates `aws_eks_addon.metrics_server` — without it, every HPA across the 5 microservices + frontend was showing `<unknown>` targets and never actually scaling, since nothing in this project (Terraform or Kubernetes manifests) was providing CPU/memory utilization metrics at all.
- **`gitops.tf`** — `helm_release.argocd` (namespace `argocd`, `timeout = 1200` — 900s wasn't enough for a real `terraform destroy`'s Helm uninstall to be acknowledged even though the actual work finished; `server.replicas`/`repoServer.replicas`/`controller.replicas` all `1`, `redis-ha.enabled = false` — single-replica everything, no HA, consistent with tech-demo scale not production) and `helm_release.argo_rollouts` (namespace `argo-rollouts`, `timeout = 300`, `controller.replicas = 1`, `dashboard.enabled = false`). Neither chart's actual `Application`/`AppProject`/`ApplicationSet` objects are applied here — that's root `argocd.tf`'s job, via `kubectl_manifest`.
- **`grafana-secret.tf`** / **`monitoring-basic-auth-secret.tf`** — two near-identical `random_password` (24 chars, no special) + `aws_secretsmanager_secret` + `aws_secretsmanager_secret_version` triples: Grafana's admin password (`/bookstore/grafana-admin`) and a shared basic-auth credential for Prometheus/Alertmanager (`/bookstore/monitoring-basic-auth`) — neither of the latter two ships with built-in auth of its own, so without this credential anyone in `monitoring_admin_cidr` could hit either UI/API with zero login, including silencing firing alerts via Alertmanager's API directly. Both gated by `count = var.create_monitoring_secrets ? 1 : 0` and carry an optional `dynamic "replica"` on `var.replica_region` — the `dr` branch's `module.eks_addons_dr` passes `create_monitoring_secrets = false` (reuse the primary's cross-region replica instead of creating a colliding second secret) and `replica_region = ""` (nothing further to replicate from the DR side). See Part 5.
- **`role_name_suffix`** (this module's own `variables.tf`, default `""`) — appended to `aws_iam_role.aws_lb_controller`'s and `aws_iam_role.external_secrets`'s names. IAM roles are account-global, not region-scoped, so instantiating this module twice (`module.eks_addons` + `module.eks_addons_dr`) without it collides outright on `CreateRole` — confirmed live on the `dr` branch's first two-region apply (`EntityAlreadyExists`). The `dr-standby.tf` call passes `role_name_suffix = "-dr"`. See Part 5.
- **`observability.tf`** — just a comment file now (4 lines), explaining the monitoring stack lives entirely on the dedicated EC2 instance, not here.

### `monitoring-ec2`
`data.aws_ami.ubuntu` — filtered lookup (`ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*`, owner `099720109477`/Canonical, `most_recent = true`), not a pinned AMI ID.

`aws_security_group.monitoring`: ingress SSH (22), Grafana (3000), Prometheus (9090), Alertmanager (9093) — all scoped to `var.admin_cidr_blocks` (defaults `0.0.0.0/0`, meant to be narrowed) — plus Loki (3100) scoped to the whole VPC CIDR (Fluent Bit on EKS nodes pushes here). Three *more* rules (`aws_security_group_rule`) attach to the **EKS cluster's own security group**, not this instance's — `eks_scrape_node_exporter` (9100, source = monitoring SG), `monitoring_scrape_eks_api` (443, so `kube-state-metrics` can reach the API server — genuinely missing until this was added; the entry existed but every connection timed out at the SG layer, confirmed on a cluster that had been through several destroy/recreate cycles with this apparently never having worked), and `monitoring_scrape_kubelet` (10250, for the cAdvisor scrape job).

IAM: `aws_iam_role.monitoring` + inline policy scoped to `ec2:DescribeInstances`, `eks:DescribeCluster`, and `secretsmanager:GetSecretValue` on exactly the 3 secret ARNs it's handed (Grafana admin, monitoring basic-auth, Alertmanager SMTP). Both the role AND `aws_iam_instance_profile.monitoring` carry a `role_name_suffix` variable (default `""`, appended to `bookstore-monitoring-ec2`) for the same reason `eks-addons`'s IAM roles do — account-global IAM names colliding between `module.monitoring_ec2` and the `dr` branch's `module.monitoring_ec2_dr`, confirmed live and fixed with `role_name_suffix = "-dr"` at that call site (see Part 5). EKS access: `aws_eks_access_entry.monitoring` + `aws_eks_access_policy_association.monitoring_view` (`AmazonEKSViewPolicy`), bound to the `monitoring-metrics-readers` Kubernetes group rather than the raw principal ARN — an assumed-role session's k8s username embeds the specific EC2 instance ID, so binding RBAC directly to that username would break on every instance replacement; binding to the group (set by this access entry, tied to the IAM role, not the instance) keeps `observability-rbac.tf`'s grants stable across replacement.

`tls_private_key.monitoring_ssh` + `aws_key_pair.monitoring` — auto-generated SSH keypair (the instance had no way to authenticate SSH at all until this was added, matching the SG's own missing-port-22 fix); `make monitoring-key` fetches the private key from Terraform state, saved locally as `.monitoring-ssh-key.pem` (gitignored).

`aws_instance.monitoring`: `t3.small`, public subnet, `associate_public_ip_address = true` (intentional — SG restricts to `admin_cidr_blocks`, and an EIP is needed for the monitoring UIs to be reachable at all), `user_data_replace_on_change = true` (fully stateless/rebuildable box — a user-data script change replaces the whole instance, correct behavior here since the entire state is Docker Compose + auto-imported dashboards, nothing to preserve). `user_data_base64 = base64gzip(templatefile(...))` — gzip'd specifically because EC2's 16KB user-data limit applies to the *compressed* bytes, and the plain-text script kept bumping against that limit as features got added.

**What `user-data.sh.tftpl` (~740 lines) actually does, in order:**
1. Installs Docker (from Docker's own apt repo, not Ubuntu's default — `docker-compose-plugin` only exists there) + `awscli`/`jq`/`apache2-utils` (the last for `htpasswd`, needed to bcrypt-hash the Prometheus/Alertmanager basic-auth password — both tools' `--web.config.file` format requires a bcrypt hash, not plaintext).
2. Installs `kubectl` v1.31.0.
3. Fetches the Grafana admin password and the monitoring basic-auth password from Secrets Manager — each in a retry loop (up to 20 attempts, 6s apart), specifically because this instance's IAM policy is created in the *same* `apply` as the instance itself, and IAM changes aren't instantly consistent; the very first boot can hit the secret fetch before the policy has propagated. Under `set -e`, an unhandled failure here used to kill the rest of the script (and the entire monitoring stack) with no automatic retry, since user-data only runs once per instance.
4. Fetches the SES SMTP credentials JSON the same way.
5. Writes `/usr/local/bin/refresh-kube-token.sh` (and runs it once immediately, then via a cron entry every 10 minutes) — generates a fresh kubeconfig (`/opt/monitoring/kube/config`, static bearer token from `aws eks get-token`) for the `kube-state-metrics` Docker container, and a separate plain token file (`/opt/monitoring/kube/token`) for Prometheus's own `bearer_token_file` scrape auth. Restarts the `kube-state-metrics` container on every refresh, since it loads the kubeconfig once at start and never re-reads it — a stale token otherwise sticks forever.
6. Writes `/usr/local/bin/update-prom-targets.sh` (run once, then every 5 minutes via cron) — calls `aws ec2 describe-instances` filtered by the `eks:cluster-name` tag to build Prometheus `file_sd_configs` target files for node-exporter (port 9100) and kubelet (port 10250), so node adds/removals get picked up without a Prometheus restart.
7. Writes Prometheus's config (`prometheus.yml`): 30s scrape/eval interval, alertmanager target with basic auth, `rule_files` pointed at `/etc/prometheus/rules/*.yml`, and 5 scrape jobs — `prometheus` (self), `kube-state-metrics` (static target), `node-exporter` (via the file_sd targets from step 6), `kubelet-cadvisor` (same file_sd mechanism, plus bearer-token auth, scraping `/metrics/cadvisor` for real per-pod CPU/memory — `kube-state-metrics` only ever has requests/limits/status, never actual usage), and `app-metrics` (`kubernetes_sd_configs` with `role: pod`, scraped through the EKS API server's pod-proxy endpoint since pod IPs aren't reachable from outside the cluster network — `relabel_configs` keep only pods annotated `prometheus.io/scrape: "true"`).
8. Writes `web.yml` (Prometheus's own basic-auth bcrypt hash) and the alerting rules file (`rules/bookstore.yml`) — 9 alerts: `NodeDown`, `HighCPUUsage`, `HighMemoryUsage`, `PodCrashLooping`, `KubeStateMetricsDown`, `HighPodCPUUsage`, `HighPodMemoryUsage`, `HighRequestRate`, `HighErrorRate` (the last two read each service's own `http_requests_total` prom-client counter — see `scripts/simulate-load.sh` in Part 3 for how to trip them on demand).
9. Writes Alertmanager's config: SMTP via the SES credentials from step 4, a route tree splitting `critical` (1h repeat) from everything else (6h repeat) by the `severity` label, two receivers (`default-webhook`/`critical-webhook`) each pointing at a placeholder `http://localhost:5001/` webhook (swap for a real Slack/PagerDuty/SNS endpoint) plus an `email_configs` block to `SMTP_TO`, and an `inhibit_rules` block suppressing `warning`-severity alerts when a matching `critical` one is already firing for the same `alertname`/`instance`.
10. Writes Loki's config — filesystem storage backend, `boltdb-shipper` index, `replication_factor = 1` (single-node, no clustering — matches the single-EC2 design).
11. Writes Grafana's datasource provisioning config: Prometheus (default datasource, basic-auth wired in via `secureJsonData`), Loki (no auth needed — same box), Alertmanager (`jsonData.implementation = "prometheus"`, wires Grafana's own native alerting UI to read Alertmanager's state, also basic-auth'd).
12. Writes the Docker Compose file itself (5 services — `prometheus`, `kube-state-metrics`, `loki`, `alertmanager`, `grafana`, all `restart: unless-stopped`, 4 named volumes for persistence across container restarts) and runs `docker compose up -d`.
13. Kicks off `/usr/local/bin/import-grafana-dashboards.sh` in the background (`nohup ... &`) — see below.

**Where the Grafana dashboard ID actually lives** (the specific question): `import-grafana-dashboards.sh` — written by the same `user-data.sh.tftpl` template, run once in the background after Grafana passes its own health check — defines a local `import_dash(id, rev, ds_input)` function and calls it exactly once:

```
import_dash 1860 37 "DS_PROMETHEUS"  # Node Exporter Full
```

**`1860`** is Grafana.com's public dashboard ID for "Node Exporter Full" (a well-known community dashboard), **`37`** is the specific revision pinned. The function downloads `https://grafana.com/api/dashboards/1860/revisions/37/download`, rewrites its datasource-input placeholder to point at this instance's own `prometheus` datasource UID, and `POST`s the result to this Grafana's own `/api/dashboards/import` endpoint via `curl -u admin:$PASS`. So the ID is a literal, hardcoded argument to that one function call, itself embedded as a heredoc inside `terraform/modules/monitoring-ec2/user-data.sh.tftpl` — not a Terraform variable, not something `scripts/configure.py` touches. The same script also directly PATCHes that dashboard's `$job`/`$node` template variables afterward (`POST /api/dashboards/db`) once a real node shows up in Prometheus — dashboard 1860 saves those two variables with no default value, and they never self-populate, so every panel would otherwise interpolate `job=""` and stay permanently empty.

The other two dashboards provisioned have **no ID at all** — they're not from grafana.com's library. `pod-node-resources.json` and `k8s-cluster-overview.json` are custom-built dashboard JSON files checked directly into the repo at `terraform/modules/monitoring-ec2/dashboards/*.json`, read via `file()` in this module's `main.tf` (`custom_dashboard_json`/`cluster_dashboard_json` template variables passed into `user-data.sh.tftpl`) and written straight to Grafana's file-provisioning directory (`/etc/grafana/provisioning/dashboards/`, configured by the `dashboards.yaml` provider config from step 11 above — folder `Bookstore`, `updateIntervalSeconds = 30`). Grafana's file provisioner picks these up automatically on boot; no API call, no download, no ID involved. (A third grafana.com dashboard, ID 315 — "Kubernetes cluster monitoring" — was tried at some point and dropped: its `$Node` variable queries a label, `kubernetes_io_hostname`, that doesn't exist anywhere in this setup's actual metric labeling. `k8s-cluster-overview.json` is the custom replacement built against metrics this setup really exposes.)

## Part 3 — Shell scripts (`scripts/*.sh`)

Everything else in `scripts/` is Python, already covered inline above — those are all invoked BY Terraform itself, via `local-exec` provisioners (`interpreter = ["python3"]`). These three `.sh` files are different: Terraform never touches them. They're run by hand, per `docs/DEPLOYMENT.md`'s numbered steps.

### `scripts/init-backend.sh` — DEPLOYMENT.md Step 2, once per AWS account
Region resolution, in priority order: an explicit CLI arg (`./scripts/init-backend.sh us-west-2`) → `AWS_REGION` from `config.env`, if it exists → `us-west-1` as a last resort. Reads the account ID via `aws sts get-caller-identity`, derives the bucket name as `bookstore-terraform-state-${ACCOUNT_ID}` (no user input needed for the name itself), then:
1. Creates the S3 bucket if it doesn't already exist (`head-bucket` check first) — versioning enabled, AES256 default encryption, all 4 public-access-block flags on.
2. Patches `terraform/versions.tf`'s `backend "s3"` block in place with the real bucket name AND region, via `sed` into a temp file then `mv` back (not `sed -i` directly — BSD/macOS and GNU/Linux take incompatible `-i` flag syntax, so this sidesteps that entirely rather than picking one).
3. Runs `terraform init` (or `terraform init -reconfigure` if `.terraform/` already exists).

This is the *only* thing that ever writes into `versions.tf`'s backend block — see Part 1's `versions.tf` section for why that field can't just be a `var.aws_region` reference.

### `scripts/init-domain.sh` — DEPLOYMENT.md Step 3, once per domain, ever
Reads `DOMAIN` from `config.env` or an explicit CLI arg. Looks up an existing public hosted zone for that exact domain first (`route53 list-hosted-zones-by-name`, filtered strictly on `Name == '<domain>.'` and `PrivateZone == false` — a loose filter could otherwise match the *private* `bookstore.internal` zone the `route53` module also creates, in the same account). If none exists, creates one (`route53 create-hosted-zone`) and prints the 4 auto-assigned NS values to set at the domain registrar (GoDaddy, Namecheap, etc.) — this is the manual, outside-Terraform step that makes `module.route53`'s `data "aws_route53_zone" "public"` lookup actually resolve to something real. Idempotent — safe to re-run any time (e.g. after a fresh checkout), it just reports `[skip]` if the zone's already there.

### `scripts/simulate-load.sh` — not part of the deploy flow at all
A demo/load-generation helper, unrelated to provisioning anything. Two independent simulations (either or both, `--cpu-only` / `--traffic-only`, default both for 180s at ~20 req/s):
- **CPU**: a throwaway `polinux/stress` pod in the `default` namespace (`kubectl run ... -- stress --cpu 2`), meant to trip `HighCPUUsage`/`HighPodCPUUsage`.
- **Traffic**: a sustained `curl` loop straight at the ALB's own hostname (read directly off the `bookstore-ingress` Ingress object's `.status.loadBalancer.ingress[0].hostname` — not `terraform output`, since the ALB isn't a Terraform-managed resource at all, it's created by the AWS Load Balancer Controller reconciling that Ingress), `Host: api.bookstore.<domain>` header set explicitly so the ALB's host-based routing sends it to `api-gateway`. Meant to trip `HighRequestRate`/`HighErrorRate`.

Polls `http://$MONITORING_IP:9090/api/v1/alerts` every 15 seconds for the duration and prints whatever's currently `firing`, so the alerting pipeline's effect is visible in the terminal without needing to open Grafana. Always cleans up after itself (stress pod deleted, background `curl` loop killed) via a `trap ... EXIT INT TERM`, even on Ctrl-C or a mid-script error.

## Part 4 — Apply order (real dependency graph, not file order)

See `terraform-execution-flow-prompt.txt` (also gitignored) for the diagram version of this. In short:

1. **Stage 1 (parallel, no deps):** `network`, `ecr`, `iam.tf`
2. **Stage 2:** `security` (needs `network`'s VPC ID)
3. **Stage 3 (parallel):** `rds` and `eks` (both only need `network` + `security`)
4. **Stage 4 (parallel):** `eks-addons`'s 4 Helm charts (ESO, ALB Controller, ArgoCD, Argo Rollouts)
5. **Stage 5:** ArgoCD's own `kubectl_manifest`s (AppProject → Application/ApplicationSet), then `wait_for_alb_hostname` polls for the real ALB
6. **Stage 6 (parallel):** `route53` (needs the discovered ALB hostname) and `monitoring-ec2` (only needs the Grafana secret, not the full `eks-addons` wait)
7. **Stage 7:** `ingress-cert.tf`'s ACM validation (only needs `route53`'s hosted zone, could technically start earlier — shown last because DNS propagation is usually the slowest single step)

Optional/independent of the above: `cloudfront.tf` (off by default), `dr.tf` (off unless `dr_kms_key_id` is set).

## Part 5 — DR standby (`dr` branch, `terraform/dr-standby.tf` + `terraform/providers-dr.tf`)

Everything below is `count = var.enable_dr_standby ? 1 : 0` (or a `for_each`/`dynamic` guarded the same way) — off by default, zero extra resources, zero cost, and the primary single-region apply's plan is unchanged when the flag is off. Turned on via `make dr-plan`/`make dr-apply`/`make dr-destroy` (pass `-var enable_dr_standby=true` on the CLI, deliberately not via `terraform.tfvars` — `scripts/configure.py` fully regenerates that file every run and doesn't know this variable exists, so a manually-appended tfvars line silently vanishes the next time `configure.py` runs; the `make dr-*` targets sidestep that trap entirely). See `docs/DR-STANDBY-PLAN.md` for the full design rationale and `docs/DR-FAILOVER-RUNBOOK.md` for the manual promotion/cutover steps — this section is just what's actually in the Terraform.

**Design shape**: a second, mostly-independent copy of the primary stack in `var.secondary_region` (default `us-west-2`), wired so the two regions apply *concurrently*, not one-after-the-other — nothing in `dr-standby.tf` depends on the primary modules except `aws_db_instance.dr_replica` (needs `module.rds.rds_instance_arn` to exist first) and the DR ACM cert's validation records (written into the *primary's* public zone, since Route53 zones aren't regional). A both-flags apply is roughly `max(primary, DR)` wall time, not the sum — use `-parallelism=20` (the `make dr-*` targets already do) since the resource count nearly doubles.

### `providers-dr.tf`
Three provider aliases (`helm.secondary`, `kubernetes.secondary`, `kubectl.secondary`), all reading connection details off `module.eks_dr[*]` via `one(...)`/`try(...)` — when the flag is off, `module.eks_dr` has zero instances, `one(...)` returns `null`, `try(...)` falls back to `""`, and the providers stay configured-but-unused (every resource that would use them is itself count-gated to 0). `aws.secondary` isn't declared here — it already lives in `providers.tf`, unconditionally configured from `var.secondary_region` regardless of the DR flag (needed by `modules/ecr`'s replication and `dr.tf`'s backup replication too).

### `dr-standby.tf`
In dependency order:
- **AZ/subnet locals** (`local.dr_az_a`/`dr_az_b`, `local.dr_public_subnets`/`dr_private_subnets`) — mirrors `locals.tf`'s primary-region layout exactly, same CIDR block (`170.20.0.0/16` — harmless, since regions are network-isolated and this stack doesn't peer them).
- **`null_resource.cleanup_eks_networking_dr`** — the DR-region mirror of root `main.tf`'s own `cleanup_eks_networking`: same orphaned-ENI/cluster-SG destroy-time hazard, same fix shape, `module.eks_dr` depends on it. Region-parameterized via `triggers`, boto3-only (no kubectl).
- **`module.network_dr`**, **`module.security_groups_dr`** — the `network`/`security` modules called a second time with `providers = { aws = aws.secondary }`, swapping the *entire* module instance onto the secondary region (simplest possible approach — works because these two modules only ever need one region's worth of resources per call, unlike `route53` below).
- **`module.eks_dr`** — cluster name `bookstore-eks-dr`, same version (`1.31`), `prefix = "bookstore-dr"`, node sizing from `var.dr_node_{desired,min,max}_size` (defaults 2/1/3 — smaller than primary's 3/1/3, a cost-conscious hot-standby that gets scaled up on a real failover, per the runbook).
- **`module.eks_addons_dr`** — same 4-Helm-chart module as primary, `role_name_suffix = "-dr"` (bug #4 in the table below) and `create_monitoring_secrets = false` / `replica_region = ""` (reuse the primary's cross-region secret replicas instead of creating a second, colliding one).
- **RDS cross-region read replica** — `aws_kms_key.dr_rds` (a CMK is required for the *destination* side of a cross-region encrypted replica even though the source uses an AWS-managed key), `aws_db_subnet_group.dr_replica` + `aws_security_group.dr_replica` (bug #3: an em-dash in this SG's description broke `CreateSecurityGroup`'s ASCII-only validation), then `aws_db_instance.dr_replica` itself — `replicate_source_db = module.rds.rds_instance_arn` (cross-region replication needs the source's ARN, not just its identifier), `db.t3.micro`, read-only until manually promoted (`aws rds promote-read-replica`, a runbook step, never automated).
- **`aws_route53_zone.dr_rds_private` + `aws_route53_record.dr_rds_endpoint`** — the DR region's own private zone, same record name (`db.bookstore.internal`) the primary's private zone uses, pointed at the replica's endpoint instead. The point: DR-region services never need a config change on failover — the DNS name they already use just starts resolving to the (now-promoted) writable instance.
- **`aws_eip.monitoring_dr` + `module.monitoring_ec2_dr`** — the DR region's own independent Prometheus/Grafana/Loki/Alertmanager stack (the primary's monitoring box is, definitionally, in the region that just died). `role_name_suffix = "-dr"` (bug #4), reads the primary's replicated secrets by name (`grafana_admin_secret_arn` etc. built from `local.dr_secret_arn_prefix` + a wildcard suffix, since Secrets Manager appends a random 6-char suffix to every secret name).
- **`aws_acm_certificate.ingress_dr` + validation + `aws_acm_certificate_validation.ingress_dr`** — a second ACM cert, `aws.secondary` provider (ACM certs are regional, the ALB needs one in its own region), same domain/SANs as the primary cert. Its DNS validation records go into the *primary's* (global) public zone — `allow_overwrite = true` handles the fact that both certs validate against the same domain, so the CNAME name/value pairs can genuinely overlap.
- **DR ArgoCD bootstrap** (`kubectl_manifest.argocd_appproject_dr`/`application_dr`/`applicationset_microservices_dr`) — same `file()`-off-local-disk pattern as root `argocd.tf`, reading `k8s/argocd/dr/*.yaml` instead of `k8s/argocd/*.yaml`. A fully independent ArgoCD instance in the DR cluster (not a hub-spoke setup) — simplest, most failure-isolated: the DR cluster's own sync doesn't depend on the primary's ArgoCD being reachable at all.
- **`null_resource.wait_for_dr_alb_hostname` + `data.kubernetes_ingress_v1.dr_bookstore`** — the DR-region mirror of `argocd.tf`'s own ALB-discovery pattern, `KUBECONFIG` pointed at an isolated `.terraform/kubeconfig-dr` file (so a concurrent two-region apply's `kubectl` calls never race a shared `~/.kube/config` current-context). Feeds `local.dr_discovered_alb_dns`, which `main.tf` wires into `module.route53`'s `secondary_alb_dns` — see bug #2/#5 below for why that wiring needed two separate fixes.

Full narrative in `docs/DR-STANDBY-PLAN.md`'s own "Bugs found + fixed" section — summarized here since it's directly relevant to reading this file:

| # | Resource | Problem | Fix |

### Apply order for a `-var enable_dr_standby=true` run
Primary chain: identical to Part 4 above, unchanged.
DR chain, running *concurrently* with the primary chain (not after it):
1. `network_dr` / `security_groups_dr` (parallel with primary's Stage 1/2)
2. `eks_dr` (parallel with primary's `eks`, Stage 3) — plus `dr_replica`'s KMS key/subnet group/SG, which don't wait on EKS at all
3. `eks_addons_dr` (parallel with primary's `eks-addons`, Stage 4)
4. DR ArgoCD bootstrap → `wait_for_dr_alb_hostname` (parallel with primary's Stage 5)
5. `aws_db_instance.dr_replica` — the one DR resource that DOES wait on the primary: needs `module.rds.rds_instance_arn` to exist first, so it can't start before primary Stage 3 finishes
6. `module.route53`'s `secondary` record — waits on `local.dr_discovered_alb_dns`, i.e. step 4 above finishing

### Destroy order for the DR stack
Same hazard shapes as the primary teardown (Part 4's "Destroy order" below), each mirrored with its own DR-region-scoped safety net: `cleanup_eks_networking_dr` (ENI/cluster-SG cleanup), `eks_addons_dr`'s own `delete_ingress_objects` (Ingress/ALB release before VPC teardown), and one genuinely new hazard — AWS refuses `DeleteDBInstance` on a source RDS instance that still has a live replica. `replicate_source_db`'s reference from `aws_db_instance.dr_replica` to `module.rds.rds_instance_arn` creates an implicit dependency edge that makes Terraform destroy the replica *before* the source automatically (no explicit `depends_on` needed) — believed correct by design, **not yet proven live**: this branch's first apply/destroy cycle stopped after a successful apply, destroy is still the next unrun step.

## Destroy order (the safety nets)

Reverse of apply, plus two deliberate safety nets that only run `when = destroy`:
- `null_resource.delete_ingress_objects` (in `eks-addons`) — deletes Ingress objects before the VPC destroy reaches them, so the ALB's finalizer doesn't hang the whole destroy.
- `null_resource.cleanup_eks_networking` (root `main.tf`) — cleans up orphaned VPC CNI ENIs + the EKS-auto-created cluster security group, after `module.eks` is gone but before `module.network`'s VPC/subnets.

Both exist because EKS and its controllers create real AWS resources directly via the EC2 API, entirely outside Terraform's own graph — Terraform has no way to know about them, let alone clean them up on its own.
